> 範圍：前端 `labor-compliance-ui` + Express proxy。後端 EAP / 資料（AI-Ready-Data）由組員維護，本文件不含後端改動。

## 二、穩定性：解決「平台會、系統卻查無」（核心修正）

### 診斷（已用 live API 實測對照，每種跑 4–5 次）

| 送出內容 | 命中 graph | 回「查無」 |
|---|---|---|
| 純問句（同平台） | 1/4 | 3/4 |
| 系統原本送的（身分前綴 + 問句 + 標註） | 1/4 | 3/4 |
| 問句 + 明確「查圖譜 + 關聯鏈」指令 | 3/5 | 2/5 |

**結論：**
- **不是專案接錯**：`.env` 指的就是 v6 咕咕嘎嘎專案（實測 IT 統計回工時 1,187、職災回完整四大表格）。
- **不是 proxy 前綴害的**：純問句與包裝過的命中率相同。
- **真因**：EAP **API 路徑的 graph 路由是「機率性」的**——v6 robot setting 的強制路由在平台 UI 有效、在 API 端大多沒被套用，單次只有約 25% 真的查圖譜，其餘掉回通用 LLM 回「查無」。平台是抽中好那次，系統一次定生死就常踩雷。

### 修法（`server/index.js`）

1. **注入「圖譜路由指令」**：每題依情境（職災走事故關聯鏈＋事故節點對照、資遣走 A006、雷達走 IT 統計三表）把 v6 robot setting 的路由規則直接寫進問句——補做 API 端沒被套用的部分（單次 25% → ~60%）。
2. **並行搶答**：同一題同時送 `EAP_GRAPH_ATTEMPTS=3` 個請求，取第一個「真的有 cyphers 且非查無」的回應，其餘取消；對前端仍以 SSE 回傳，`askStream.js` 不用改。

**驗證**：透過新 proxy 實打 live API，職災問句 **命中率 3/3**（修前 1/4），每次 144–284 cypher 列、完整四大表格、零查無。

> 註：穩定性來自「搶答」，不是提示詞，所以**專案 robot setting 不需要再改**（owner leader57 才能改、且純提示詞拉不到穩定）。

## 三、聊天 UI 精修

### 1) GraphRAG 推理路徑：改 schema 無關（保留，不移除）
- 問題：舊「路徑視角」寫死只認 `裁罰案例_*` 欄位（事故/裁罰/法條），職災問句的 cypher 是刑責/法規/義務節點，欄位對不上 → 三格全 0 項，看起來壞掉。
- 修法：`src/lib/reasoningPath.js` 改成從回傳列的欄位前綴（`Category_屬性`）**動態歸納「本次命中的圖譜節點類型 + 各類數量」**，並跨所有查詢彙整；有裁罰案例時仍保留可展開案例卡；「技術視角」原始 Cypher 不動。
- 連帶：`ReasoningDrawer.jsx` 計數單位/顏色泛用化；`EvidenceArea.jsx` 文案由「共 0 件相關案例」改為「已實際查詢知識圖譜的節點與關係（有案例才補件數）」。

### 2) 參考來源：節點編號 → 中文名稱
- 問題：📄 參考來源 chips 直接顯示 `DOC001…DOC010`。
- 修法：新增 `src/data/docNodes.js`（對照已驗證的 `05_文件.csv`，比照 `extractLaws.js` 的 pcode 靜態表，非假資料），把 DOC ID 還原成「診斷證明書、出勤紀錄…」並去重；未知 ID 才保留原樣（`SourceChips.jsx`）。

### 3) 延伸問題 chips：改為「依回答動態產生」
- 需求：延伸問題不要寫死，要像參考來源那樣由回答產生。
- 修法：proxy 標註指令多要求一段「🔎 延伸問題」（3 題、依本次回答生成）；`parseCitations.js` 解析三段標註（📄/⚖️/🔎，順序不固定也能切段、自動去條列符號與編號）；`AnswerBubble.jsx` 的延伸問題 chips 改吃 `parsed.followups`，點擊直接送出（走同一條 ask、含並行搶答）。已移除 `scenarios.js` 內寫死的 followups。
- 驗證：live 確認命中 graph 的回答會輸出 🔎 區塊並正確解析成 chips。

## 五、決賽值得講的亮點

1. **把評審的核心批評正面解掉**：評審說「問問題吃不到那些資料」。我們先做了 live 對照實測，定位真因是「EAP API 的 graph 路由是機率性的」——不是資料壞、也不是問法錯，而是平台層的不確定性。這個診斷本身就展現工程嚴謹度。

2. **工程化的穩定性解法（最大亮點）**：用 proxy 層「圖譜路由指令注入 + 並行搶答」把一個機率性後端，變成 demo 可重現的穩定系統（單次命中 25% → 實測 3/3）。這是「Vibe Coding 不只是串 API，而是工程補強平台短板」的具體展示。

3. **證明『真的有用 GraphRAG』**：推理路徑（動態反映本次命中的節點類型與數量）+ 技術視角（真實 Cypher 全文），直接攤開「這題走了哪些圖譜節點」，回應評審質疑、也凸顯 Graph 相對純 Vector 的推理價值。

4. **同一知識庫、雙視角**：資方看「法定義務／免責／舉證／罰鍰」，勞工看「可主張權益／給付／申訴管道／時效」——身分前綴在 proxy 注入，一個大腦兩種立場，現場可並排對照。

5. **報告 / 摘要分流**：案件調查＝留在系統的互動底稿（精確到期日、資遣費試算、風險燈號）；諮詢摘要＝可攜出的文件（資方＝盡職調查紀錄、勞工＝維權行動指南，可下載 Word/PDF）。

6. **可信度設計**：法條一律連全國法規資料庫官方原文；參考來源還原成中文文件名；延伸問題依回答動態生成；無真實裁罰資料時誠實標示、不造數字。

7. **IT 過勞主軸有數據後盾**：資訊服務業違規第一名就是工時/加班類 **1,187 件**（> 投保類 687 件），主軸不是喊口號、是同業裁罰統計撐起來的。

## 六、Proxy 技術說明與報告取捨

### 定位（一句話）
前端與 EAP 之間的「安全 + 穩定」中介層：藏金鑰、解 CORS、把問句加工成「一定走 graph」、再用並行搶答補平台的不穩定。檔案：`server/index.js`（約 256 行）。

### 資料流

```
前端 askStream → POST /api/ask {question, role, scenario}
   → buildQuestion() 組裝問句(圖譜路由指令 + 身分前綴 + 標註指令)
   → askWithRacing() 同時發 3 個 runAttempt()
        每個 = chat/create → chat/{id} streaming → 緩衝整段
   → 取第一個「真的有 cyphers 且非查無」的回應(isGraphHit)
   → 以 SSE 回傳前端(progress 心跳 → 切塊 chunk → 最終 result + cyphers)
前端 parseCitations / extractLaws / reasoningPath 解析 result + cyphers 渲染
```

### 五個職責 → 程式碼對應

| 職責 | 在哪（server/index.js） |
|---|---|
| 1. 藏 token / project_id（只在 server env，不進前端 bundle） | 設定 `:15-19`、`eapHeaders()` `:62` |
| 2. 解 CORS（瀏覽器不直打 cloud.geminidata.com） | proxy 本身存在；`/api/ask` 路由 `:190` |
| 3. 問句加工：圖譜路由指令 + 身分前綴 + 標註指令 | `buildQuestion()` `:56`；`GRAPH_DIRECTIVE`(情境化) `:29`、`ROLE_PREFIX`(資方/勞工) `:41`、`ANNOTATION_INSTRUCTION`(📄/⚖️/🔎) `:50` |
| 4. **並行搶答（核心穩定性）** | `askWithRacing()` `:138`、`runAttempt()` `:71`、`isGraphHit()` `:132`、`REFUSAL_RE` `:54` |
| 5. 對前端 SSE 回傳（前端零改動） | `/api/ask` handler `:190-253` |

前端對接：`src/services/askStream.js` 解析 SSE；`src/features/chat/AnswerBubble.jsx` 用 `parseCitations`/`extractLaws`/`reasoningPath` 把 result+cyphers 渲染成法條卡片、參考來源、推理路徑、延伸問題。
